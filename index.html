WiPPY

用自然語言規劃活動訊息，AI 幫你寫好、排好、推出去。

AI 驅動的活動管理與訊息推播平台。透過 7 階段 Harness Pipeline， 讓每一次 LLM 呼叫都可觀測、可恢復，並透過 LINE Bot 自動推播給對的群組。

對話示範
Agent 對話 · 五月露營活動
你
我有一個漂書活動，五個朋友，五月一號要在匹客球場換書。我想在換書前這幾天（大概從今天到五一當天）在 LINE 群組裡推一些東西，讓大家進入狀態，因為這個活動的氣氛很重要——不是那種很熱鬧的活動，是比較安靜、有點文學感的東西。

我大概有幾個想法：
想提醒大家帶書、帶小卡，但不要太直白，感覺太像通知
想推一些有氣氛的東西，比如書摘或句子，讓大家慢慢有感覺
AI Agent

要創造這種「安靜且有文學感」的氛圍，關鍵在於「留白」與「隱喻」。不要把這當成一個「活動」，而是一場「默契的約定」。以下我為你設計了從 4/27 到 4/30 (活動前一天) 的引導邏輯與文案範例。這些內容請用一種「隨手分享」的口吻發在群組裡。

預熱時間表

4/27（一）：關於「書架上的安靜」
  • 目的：讓大家開始意識到要帶書，但不說「請帶書」。
  • 文案：（發一張你書架的照片，或是網路上很有意境的閱讀角落圖）
    「這幾天整理書櫃，發現有些書讀完後，在架子上站了很久，安靜得像是在等什麼。突然想到，也許它們也在期待一趟新的旅行，去看看誰會是下一個翻開它們的人。」
4/28（二）：關於「對話的痕跡」
  • 目的：隱晦帶出「小卡」的意義。
  • 文案：（分享一段書摘）
    「以前看書，總喜歡在空白處寫下當時的註解。後來覺得，如果能把這些心情留給下一個讀者，就像是和未來的某個朋友跨越時空對話。如果這兩天有人挑選書的話，不妨也留下一張小卡吧，算是給這本書的一點告別，或是給下一站的祝福。」
4/29（三）：關於「流動的意義」
  • 目的：連結匹客球場與環境，強調靜謐感。
  • 文案：「這幾天一直在想，我們選在球場旁見面，在那種甚至還聽得見遠處揮拍聲的環境裡，讀著這些交換來的文字，應該會有一種很特別的沈澱感。書本像水一樣，就是要流動，才會有生命。」
4/30（四）：關於「不期而遇的懸念」
  • 目的：為明天的「規則」埋下伏筆。
  • 文案：「明天要見面了。關於這些書怎麼到下一個人手中，我心裡有個小想法，想試著讓過程多一點點不確定性，讓一切順著當時的直覺發生。明天見面時再和你們說。」

你覺得這個節奏符合你們的朋友圈嗎？
確認沒問題的話，請讓我知道。

你
很好，放進排程
AI Agent
✅ 已將 4 則推播訊息加入排程！請到「推播企畫」分頁確認後點「批准」，訊息就會在指定時間自動發出。
常見問題
訊息到了時間卻沒發出去，怎麼辦？
最常見原因是忘記點「批准」。請到「推播企畫」分頁確認審核狀態是否為「已批准」。若已批准仍未發送，請確認 LINE Bot 是否仍在目標群組中，並到「發送紀錄」查看錯誤訊息。
AI 產出的內容不夠精準，怎麼改善？
在「知識庫」分頁補充更多背景資訊：活動特色、注意事項、目標受眾、語氣要求等。知識庫越詳細，AI 產出的內容就越符合期待。
可以針對不同群組發送不同內容嗎？
可以。在 Agent 對話中直接說明：「A 群組收到○○，B 群組收到△△」，AI 會幫你分開建立兩組排程。
02 · 問題與解法

為什麼要做 WiPPY？

讓活動主辦方專注於活動本身，僅需審查 AI 規劃的不同群組的客製推播文案、推播時機

Pain Points

  • 手動撰寫推播文案，耗時且難以維持一致性
  • 排程邏輯散落各處，缺乏可觀測性
  • 知識庫與歷史對話沒有系統性管理

WiPPY 的解法

  • 自然語言輸入，Agent 自動產生訊息計畫
  • 7 階段 Pipeline，每步可觀測、可恢復
  • Firestore 知識庫 + 對話歷史，context 有記憶
03 · 核心架構

(非常簡陋的) Harness Pipeline

7 階段有狀態執行器。每次執行都建立一筆 harnessRun， 記錄當前 stage、LLM 呼叫次數與狀態，讓 debug 不靠猜。

04 · 三種輸出類型

Output Intent

parse_output 階段事後推斷 intent，決定後續行為。每種 intent 對應不同的副作用。

plan_messages

訊息排程計畫

產生訊息排程，寫入 Firestore 並準備推播至目標 LINE 群組。

副作用 → 寫入排程 + 觸發推播
extract_knowledge

知識萃取

從對話中萃取結構化知識，更新群組知識庫，供下次 context 載入使用。

副作用 → 更新知識庫
general_chat

一般問答

回答使用者的問題，純文字回覆，不觸發任何 Firestore 寫入。

副作用 → 無

06 · 下一步

Roadmap

分為技術強化與功能擴充兩條軸線，持續迭代。

技術強化
Phase 2 Recovery 與 Safety 強化
將 validateExtractedKnowledge() 接進 orchestrator 的 validate_output stage
建立分層錯誤分類（context_load_error / llm_rate_limit_error / persistence_error），每類有明確 retry 策略
persist_effects 多批寫入加補償邏輯，依 runId 重試未完成的批次
Scheduler / send path 套入相同的 retry + structured failure policy
Phase 3 LangGraph-ready
每種 intent 有獨立 prompt mode（plan_messages / extract_knowledge / general_chat 各自的 system prompt）
將每個 stage 顯式化為 tool contract（name、input/output schema、timeout、retry policy），為接 LangGraph 做準備
ContextEnvelope 生成器替換為 retrieval-augmented 版本，召回相關知識而非全量載入
明確標註 pause hook（pause_before_persist、pause_after_validate）對應 LangGraph human-in-the-loop 中斷點
功能優化及擴充
Phase 2 知識庫與 Prompt 優化
優化知識庫可輸入類型及輸入方式，擴增不同格式檔案及串接方式
優化現有 System Prompt 的約束條件、產出格式、錯誤處理
Phase 3 個人化風格與意圖判斷
增加各群組個人化風格蒐集及紀錄機制，以供 LLM 針對不同群組產出不同調性的推播內容
